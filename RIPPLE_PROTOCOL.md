# RIPPLE v0.1: TINY → BIG → TINY → BIG

The purpose is to prevent concept drift, hidden dependency assumptions, cross-project identity erosion and unproven promotions.

### R0 · Recover (tiny)
Read authoritative source at known SHA, Library checkpoint and last receipt. Detect collisions and old claims. Preserve historical artifacts. Stop on missing authority.

### R1 · Inspect and select (tiny)
Pick **one** bounded change with a reproducible failure or measurable benefit. Write target contract and acceptance criterion. Do not invent code to fill missing source.

### R2 · Local vertical slice (tiny)
Implement the smallest reversible update on isolated branch/copy. Keep input/output, risks and ownership explicit. Do not replace original audio/evidence.

### R3 · Verify (big integration probe)
Run unit/integration/adversarial tests on the exact source hash. Attempt one actual adapter transaction to independent peer ONLY if both contracts are available and authorized. If absent, record a blocked integration, not a pass.

### R4 · Reconcile (tiny)
Compare observed outcomes to intent. Record what failed and a single forensic probe. Preserve previous receipts, reject unsupported proof, include independent test when possible.

### R5 · Package (big)
Save append-only evidence and source diff. Produce an immutable archive, SHA-256 manifest, rollback, notes, accepted vs rejected proposals, and separate real-host/device acceptance.

### R6 · Publish candidate (guarded)
If sanitized and permitted, publish a review branch or PR, never unreviewed protected branch. Public collaborators only see alias status; private mapping lives in Library. Never publish secrets, personal data, unlicensed third-party code, or external collaborators' source.

### R7 · Next ripple
Choose the next weakest verified dependency or nearest useful blocked gate. Don't spin on restyling, rename a project, or grow architecture without new evidence.

## Quality gates
`source-known → runnable → tested → host-verified → user-accepted → release`. These are not equivalent. Use `unknown/blocked` rather than guessing. At every stage record source SHA, environment, command, pass/fail, changed paths, rollback and risk.

## Cadence
Scheduling does not imply the runtime remains online or has Git/write access in future runs. Each scheduled iteration must re-open the latest checkpoint and leave a standalone receipt. Work automatically up to explicit permissions; self-modification, publishing private code, protected integrations and production operations require their own approval.

## RIPPLE 2.0
Prioritize functional 40%, visual 25%, adapter 20%, security 10%, administration 5%; mandatory tests and packaging every run; functional slice every three runs or pivot; no consecutive minor hardening.
